# 源码归档与构建对应

1. 在准备交付的检出目录核对 `git status`，包含所有已批准的代码、素材、测试和文档；签名文件保持在仓库外。
2. 运行分析、测试和脚本检查后提交。版本有变化时递增构建号；不要用旧 APK 验收新代码。
3. 从干净的提交生成源码包：

   ```powershell
   python scripts/archive_source.py --output ../source-archives
   ```

   工具直接读取 HEAD 的 Git blob，保留提交中的字节及可执行权限，不采用本机检出的 CRLF/LF 转换。逐项记录路径、大小、SHA-256、Git blob 和文件模式；输出清单还记录完整提交号和 ZIP 哈希。清单位于 ZIP 外，避免自引用。已跟踪和未跟踪的修改都会阻止归档；忽略的本地缓存不会打包。已跟踪的安装包、缓存、签名配置和所有 `.env` / `.env.*` 文件都会阻止归档，不会悄悄遗漏；无秘密的配置示例请使用其他文件名。

4. 如需绕过中文路径构建限制，将归档解压到英文临时目录，显式指定持久 `PUB_CACHE`，按构建说明配置本地签名后运行正式构建。不要改动解压后的源码。保存使用的 Flutter、Dart、JDK 版本。
5. APK 交付目录保存 `SHA256SUMS` 和 `build-info.json`；后者引用源码提交、源码包及完整清单的哈希。签名密钥和本机配置不属于源码归档，应另行安全保管。

源码可追溯不代表 APK 字节必然完全可重复，也不替代设备安装、迁移或公开发布验收。只有发布后的安装包才能切换进官网 `release.json` 与 HTML 兜底下载链接。

应用 CI 在 Linux 上生成并解压源码 ZIP，检查 `android/gradlew` 的 LF 和可执行权限，再从解压目录执行严格依赖解析、分析、测试和 Android 编译。Windows 上的归档测试跳过 Linux 执行检查，该项由 Linux CI 补齐。

历史 build33 从未提交工作区构建，其原 ZIP 与 APK 保留不变；完整补充清单只能证明当时 ZIP 内容，不能追认成某个 Git 提交构建。
